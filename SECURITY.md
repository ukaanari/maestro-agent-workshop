# Security policy

MAESTRO is **experimental, pre-release software**. Its sandbox has been tested on one
macOS 26.7 arm64 host and GitHub's macOS 26.6.2 arm64 runner, against deterministic
first-party fake agents only. Trusted Local Mode runs the real Codex CLI and Claude Code
**unconfined**, as your user; only its verification step is sandboxed. Do not rely on
MAESTRO to confine untrusted or hostile code.

## Reporting a vulnerability

Please report suspected vulnerabilities **privately**, using GitHub's
**"Report a vulnerability"** button on this repository's *Security* tab (private
vulnerability reporting). Do not open a public issue for an undisclosed vulnerability.

Please include:

* the affected file and function, or the profile rule,
* the output of `python3 maestro.py doctor`, or at least the macOS version and build, CPU
  architecture, and Python and Git versions,
* a minimal reproduction, preferably an offline test in the style of
  `tests/test_security.py` (synthetic canaries in private temporary directories, no
  personal paths, no external network).

This is a single-maintainer project with no service-level commitment. The maintainer
will try to acknowledge reports within 7 days. Fixes are made on the default branch.
Tagged releases are experimental pre-releases; only the latest one is supported.

## In scope

* Escaping the Seatbelt profile generated by `sandbox.py`: reading, writing or executing
  outside the granted paths, network access, inspecting or signalling other processes.
* Reaching MAESTRO's protected state from a confined process: the SQLite database,
  marker, `repo.git`, the executor lock or `worktree/.git`.
* Bypassing the evidence gate: getting a task approved while its stored artifacts or live
  worktree differ from what was reviewed and verified.
* Validation bypasses in `ExecPolicy`, path handling, envelope or JSON decoding.
* Any path by which a task runs unconfined after the isolation check fails.
* Trusted Local: approving or exporting a patch that differs from the verified (and, when
  required, reviewed) snapshot; a review that is stale, unverified or not bound to the
  exact patch satisfying the approval gate; verification layout options that run anything
  other than the fixed `unittest` runner or escape the snapshot copy; API keys, tokens or
  other unlisted environment variables reaching Codex or Claude Code.

## Known limitations (already documented, not new findings)

These are listed in [P1A-SECURITY.md](P1A-SECURITY.md) and the README. Reports that
*demonstrate a concrete exploit* of one of them are still welcome.

* A `setsid()`/`setpgid()` or double-forked child survives process-group cleanup (#2) when `fork` is
  allowed. Fork is denied for all non-test policies.
* `sandbox-exec` is deprecated and undocumented, so semantics may change across macOS
  versions.
* `(deny default)` is not exhaustive. Small read-only information leaks remain: top-level
  `/` names, ancestor directory metadata, system libraries, the Python prefix.
* There are no memory, disk or CPU limits beyond wall-clock timeouts and output caps.
* Agents run as the same user, so a kernel or sandbox escape yields that user's access.
* The local operator and MAESTRO's own source and state directories are trusted. Hashes
  detect corruption, not an attacker who can rewrite both data and hashes.
* Git setup commands run unconfined, with fixed argv and hooks and protocols disabled.

## Out of scope

* The behaviour of the Codex CLI and Claude Code themselves. In Confined Mode their
  adapters are disabled and always refuse; in Trusted Local Mode they run unconfined by
  design, so what they do with your permissions is not a MAESTRO vulnerability.
* Non-macOS platforms. There is no isolation backend there, and tasks end `blocked` by
  design.
